# 保存した評価を次の生成に使う（2026-10-13）

完成PNGの「選択・全部使わない・理由・気になる点」を、次の画像編集APIの参考情報へ加える。画像生成モデルの重みを更新する学習ではなく、生成時に過去の評価を参照する仕組み。採点側のAssessment、重み、品質点数は更新しない。

## 操作

1. `/editor`の比較一覧で、匿名の評価者ID、選択、理由・気になる点を保存する。
2. 動画タイトルと写真を用意し、「過去の評価を次の生成へ」の評価者IDを合わせる。初期値はr01、同じ案件のdevだけを使う。
3. 表示される評価メモを確認する。不要な記録のチェックを外せる。「外した記録を戻す」で除外を解除する。別案件にも応用したいときだけ「別の案件の評価も使う」を選ぶ。
4. 有料生成の確認にチェックして、通常の生成ボタンを押す。メモの作成・確認・設定変更・評価の保存は無料。送信時には写真と現在の入力に加え、有効な理由と分類がOpenAIへ送られる。過去の写真は送らない。
5. 完成画像にメモの内容が反映されたか確認し、選択と理由を保存する。画面と履歴に今回のメモを表示し、共有ZIPにも残す。

最大6組の最近の評価を使う。同じ組の画像が多くても、その組の記録は1件。理由は500 Unicodeコードポイントまでの抜粋で、抜粋したことを記録する。気になる点をまとめた確認ポイントも表示するが、改善済みの印や採点値ではない。

対象は入力が記録された完成画像の組で、自分の評価者IDと一致し、全画像を確認した記録があり、理由または分類があるもの。新しい画像を追加したあと再確認していない記録、評価者不明、理由も分類も空の記録は使わない。案件は明示した案件名、なければ動画タイトルで照合する。写真の利用確認や正式な20件の進捗を自動で補わない。

生成ボタンを押したときに保存庫を読み直して、送るメモを固定する。読み込みに失敗した場合は有料APIを呼ぶ前に止め、画面へ理由を表示する。評価メモを無効にすれば、過去の記録を送らずに生成できる。設定は下書きと下書きZIPに保存する。有料送信への同意は復元しない。

メモを更新する保存庫の読み取りはreadonlyで、画像資産のPNG本体を取得しない。タイトル編集やチェック変更のたびに全画像を読み込み直す処理は避ける。

## 指示の優先順位と限界

過去の理由はJSONの参考データとして扱い、理由内の命令は実行しないよう指示する。現在のイメージ、構図、デザイン、修正指示、手入力の見出し、写真を保持する条件を優先する。古い動画の内容・人物・見出しを流用する指示にはしない。

画像生成と同じ1回の編集へメモを加えるため、追加のAI呼び出しや自動再生成はない。プロンプトは長くなるので、生成の実費が従来と同額になる保証はない。品質向上やメモへの追従は未検証で、人が画像を確認する必要がある。指示と保持条件を分け、修正後を見て調整する方針は[OpenAIの画像プロンプトガイド](https://developers.openai.com/api/docs/guides/image-prompting)を参照。

## 生成側・採点側で共有する契約

`POST /api/v1/complete-thumbnail`の任意項目`feedback`。省略時は以前と同じ経路。形式は`generation-feedback-1.0.0`、OpenAPIの`GenerationFeedback`と人工fixture `docs/fixtures/generation-feedback.json`を参照。

- scope: project / all、projectName: 案件名 / 全案件ならnull
- reviewerId: 匿名ID
- records: 最大6件。groupId、recordedAt、decision、selectedImageId、reason、reasonTruncated、issues、images
- images: その評価で確認した画像のimageId、imageSha256、generationVersion。画像本体は含めない。
- criteria: recordsのissuesをtext / subject / composition / otherの順で重複を除いた分類

送信時は、重複した組・画像ID、不正な日時・ハッシュ、参照先にない採用画像、分類と確認ポイントの不一致、未知の項目を拒否する。1件以上、理由か分類が必要。正規化後のJSONは24,000文字以内。サーバーはブラウザの履歴画像を持たないため、過去の選択が本人のものか、ハッシュが実画像に合うかはHTTP入力だけでは再照合できない。参照は由来の記録であり、認証や学習品質の保証ではない。

応答にはメモを指定したときだけ`feedbackApplied`を返す。正規化して指示へ加えた内容のコピーで、反映されたことの検証結果ではない。生成版は`ai-complete-0.6.1`。モデル・medium品質・サイズ・1回1枚・既存回数制限を維持する。

保存は画像ごとの`feedbackContext`（送信時の記録）と`result.feedbackApplied`。両方ある場合は一致が必要。旧サーバーの応答にechoがなくても送信記録は残す。入力不明の旧完成PNGは、復元された応答のechoだけを保持し、送信入力を推測で付けない。

評価メモのある組は`complete-comparison-1.8.0`、解析datasetは`complete-evaluation-dataset-1.7.0`。reportは既存の1.1.0。比較・共有ZIP・保存庫・解析・非公開previewで維持する。生成時のメモは画像の固定情報なので、同じ画像IDに別のメモを取り込もうとすると拒否する。現在の理由の編集は、過去の生成に使ったメモを変更しない。

写真・タイトル・内容・見出し方針・イメージによる既存組IDは変えない。同じ入力でメモあり／なしを比べられる。旧1.0.0〜1.7.0も読める。新しいメモを古い版に偽装した取り込みは拒否する。写真や実際の評価理由は非公開で扱う。

新しい静的配信は`/feedback-memory.js`と`/shared/generation-feedback.mjs`。依存追加なし。APIの任意フィールド、比較形式、解析datasetへの追加は相互レビュー対象。採点担当はメモと人の評価を見比べられるが、保存だけで採点モデルが学習したとは扱わない。


## 検証用の記録をメモへ混ぜない

groupIdのUTF-8文字列全体（complete-を含む）をSHA-256へ通し、先頭バイト<77をholdout、残りをdevとする。shared/evaluation-split.mjsのsha256-id-first-byte-77-1.0.0で、採点側sample_idと同じ方式。ハッシュの先頭を読むだけでなく、groupId自体をハッシュする。判定のために入力の組IDを変更しない。

画面のビルダーはdevだけを選び、APIのvalidateCompleteもNodeのSHA-256で再判定してholdoutを拒否する。古いsnapshotの検証・取り込みでは過去の記録を消さない。過去のholdout利用は解析のfeedbackAudit.holdoutExposuresとcontaminatedGroupIdsへ記録し、その組をブラインド効果確認から除外する。未提供・削除済みの履歴は監査できないため、分割導入前に調整に使った入力は別途本人が申告し、新しいholdoutを用意する。

評価者IDは^r[0-9]{2,}$。rabc等を別人へ自動変換しない。理由がOpenAIへ送られることと、第三者の名前・連絡先を書かないことを生成前に表示する。メモ形式は1.0.0を維持し、新しい保存項目は増やさない。生成0.6.1とOpenAPI0.3.5へ更新する。

解析dataset1.7.0では、すべての画像にfeedbackUsedとfeedbackUsageKnownを、組にsplitとsplitVersionを出す。feedbackUsedはcontext/echoの有無から計算し、利用が記録された場合はtrue。falseは記録なし。既知の生成0.0〜0.5系・0.6.0/0.6.1では利用記録が無ければメモなしとして扱い、それ以外の版や版不明はfeedbackUsageKnown:falseで対照から除外する。既知の版でも手作業で情報が削られた記録は本人が申告し、対照に使わない。利用記録は実画像への追従や改善の証明ではない。

外側の比較1.8.0・report1.1.0と旧入力は維持する。現在の解析writerは旧比較も1.7.0へまとめるが、元のgeneration_version、固定入力、snapshot、画像ハッシュは変えない。新しい分割とusageの項目は相互レビュー対象。ブラインド比較用の手順と出力物はVALIDATION-PLAN.mdを参照。
