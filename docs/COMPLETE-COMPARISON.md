# 写真から実際に作った完成PNGを比較する

2026-10-09、ユーザーからAPIで生成したものは使えるレベルだったと確認を得た。今後は実PNGの比較へ進む。確認した入力以外の写真・タイトルの品質や、20件の比較結果を確認済みとはしない。`/editor` の「AI完成画像を見比べる」は、本当にAPIが返した完成PNGを比較する画面。配置だけ変えた無料プレビューをAI生成結果として混ぜない。

## 使い方

1. 写真・動画タイトル・内容・見出しを入力し、構図の希望を選ぶ。
2. 送信と課金を確認して、1枚を手動生成する。結果は下書きと比較一覧に保存される。
3. 写真とテキストを維持し、希望する構図だけ変えて次の1枚を手動生成する。起動中の回数上限は既定1回で、比較画面が上限を広げたり自動で再生成したりはしない。
4. 「AI完成画像を見比べる」で組を選び、168 / 246 / 360pxへ表示を切り替える。表示幅は検証前の仮値で、画面が狭いと実幅は小さくなる。
5. 使いたい案、または「全部使わない」を選ぶ。理由・気になる点（文字、人物/素材、構図、その他）を任意で記録する。実表示幅も残す。
6. 各画像の実費が確認できた場合だけ、USDで入力する。確認できない場合は空欄のままにする。PNG保存結果は、実際にファイルが保存されたか確認して記録する。
7. 各完成PNGと、写真・画像・比較記録のJSONを非公開で保存する。「全組の画像・記録・集計JSONを保存」で全体も書き出せる。リロード後も、このブラウザの比較一覧から再表示できる。

同じ組にする条件は、APIへ送った1280×720の写真のバイト、タイトル、動画内容、見出しが一致すること。構図の希望は変えられる。切り取り位置、写真、テキストが変わったものは別の組にする。入力欄を生成中に編集しても、記録するのは実際に送信した内容。後から入力を推測で差し替えない。

以前の完成PNGは、次の有料生成前に保護するため比較一覧へ保存する。生成時の入力条件を持たない古い下書きは「以前の完成画像（入力条件不明）」として別に扱い、現在の入力写真や見出しを付け足さない。既に一覧にあるPNGは重複保存しない。比較一覧から削除した組は自動復元しない。編集下書きの最後のPNGは別に残るため、次の生成時には再度保護対象になる。

## 保存と限界

ブラウザのIndexedDB `thumbnail-complete-gallery` に、入力写真と組、完成画像、選択を保存する。最大6画像、入力写真と完成PNGのdata URL合計64MiBを暫定上限とする。必要なPNGとJSONを書き出してから不要な組を削除する。「写真下書き・完成画像の比較履歴を消す」は、確認後に編集下書きと比較履歴を両方消す。

前の完成PNGを保存できない場合は、次の有料APIを呼ばず理由を表示する。生成後の比較保存に失敗した場合は、生成成功と保存失敗を区別し、新しい完成PNGを表示・ファイル保存できる状態に保つ。API失敗時は前の完成PNGを維持する。再試行は自動で行わず、送信の確認チェックをリクエスト後に外す。

新しい案が増えた組では、以前の選択を残したうえで「新しい案も比べて保存し直してください」と表示する。JSONの`reviewCoversAllImages`がfalseなら、保存済みの選択は組の全画像を対象としていない。

生成時間は画面のリクエスト開始から結果取得・表示までの経過時間。古い画像は時間不明のnullで、実費をAPIレスポンスから推測しない。画像ごとの任意の`observation`に、記録時刻・実費`costUsd`（未確認はnull、確認済み無料は0）・PNG保存結果`pngSave`（unknown / saved / failed）を保存する。実費は請求・利用履歴でその生成分を確認した場合だけ入力する。過去に報告された1枚の料金を全画像に適用しない。ボタンを押した事実だけで保存成功にしない。

一覧上部に、現在保存中の画像について時間の中央値/p95、確認済み費用の合計と不明件数、PNG保存結果を表示する。p95は時間を小さい順に並べたnearest-rank（ceil(n×0.95)番目）で、少数では最大値になる。実費と保存結果は画像IDごとに更新し、同じ画像を複数回見比べても二重集計しない。生成失敗と削除済み画像を含まないため、API成功率・累計支出ではない。

1枚しかない組の記録は「1枚の確認」、全画像を見た2枚以上の組は「比較」と分ける。案が増えた後の古い記録は再確認待ちとして扱う。画像IDにひも付く人の選択が記録されるまで、会話上の品質確認を一覧へ推測で登録しない。人の正式20件の完了数は、この機能では計算しない。

## 採点担当へ渡す形式

各組JSONの版は`complete-comparison-1.1.0`、kindは`human_quality_review`。入力写真のSHA-256、固定した入力内容、完成画像のSHA-256・生成版・構図の希望・時間、任意の実費/保存結果、人の選択/不採用・理由・気になる点・実表示幅を含む。旧1.0.0の画像にはobservationがないため、費用・保存結果は未確認として扱う。既存IndexedDBの版は1のままで、画像レコードに任意項目を加える。

全組のJSONは`complete-comparison-report-1.0.0`、kindは`human_quality_report`。`sets`に画像付き各組、`summary`に上記の集計を持つ。写真・PNGを含むため非公開で渡し、Gitへコミットしない。正式な採点側への取り込み・複数ファイルを横断する集計は、相手の形式レビュー後に接続する。保存上限に達する前に書き出し、不要な組を削除して次を記録する。

完成PNGは未採点で`assessment:null`。既存Candidate/Assessmentやpreferences.csv/scores.csvとは別の記録で、採点担当の正式な20件に自動で加えない。画像資産APIやPNG分析の契約を変更せず、選択理由を生成AIや採点モデルへ自動学習させない。

serverの変更は3つの静的JS配信ルートだけ。共有API入力、OpenAPI、採点の点数・並び順・重みは変えていない。採点担当はこの非公開JSONを使って失敗例を見られるが、画像資産の正式な共有入力はPNG-ASSETS-PROPOSAL.mdの確認後に別途接続する。

検証は人工PNGのヘッダーと画面イベントのテスト。画面の復元・不採用・入力条件の固定、前の画像の保護、保存容量エラー、APIエラー、実費の未確認と0の区別、二重集計の防止、全組JSONの内容を確認した。API生成画像は使えるレベルだったとユーザーが報告済み。新しい実費/保存結果欄と実ブラウザのIndexedDBでの記録・復元は、実際に使って確認する必要がある。今回の実装・テストで有料APIを呼んでいない。
